# V1.3 Engineering Addendum - Homepage Performance Boundaries

Date: 2026-05-30

This addendum records the next homepage performance step after adding richer result actions and review workflows.

## Implemented

- Converted `CalculatorAnalyticsBeacon` from a static homepage import to a dynamic client-only import.
- Kept analytics browser-only with `ssr: false` because it only sends delayed GA events.
- Added stable-height lazy fallbacks for the projection chart and AI helper to reduce layout shift risk while chunks load.
- Split below-the-fold FAQ, calculation details, and tax-data freshness UI into dynamic chunks.
- Moved FAQ items into `src/features/faq/faq-items.ts` so FAQPage JSON-LD stays available without statically bundling the FAQ UI.
- Converted `src/app/page.tsx` back to a server component and moved calculator state, local storage, result actions, chart, AI helper, analytics beacon, and calculation details into `src/app/HomeCalculatorClient.tsx`.
- Extended homepage performance tests to guard dynamic imports and fallback sizing.

## SEO / Core Web Vitals Rationale

- The calculator and primary result area should remain the first interactive product surface.
- Tracking and below-the-fold explanation modules should not compete with first-load rendering.
- FAQ structured data should remain available in source-rendered JSON-LD even when the visible FAQ UI is loaded later.
- Static SEO surfaces should not inherit the calculator's client boundary when they do not need browser state.
- Reserving approximate loading heights helps prevent content jumps when lazy modules hydrate.

## Validation Targets

- `tests/core/homepage-performance.test.ts`
- Full `npm test`
- `npm run build`
- Desktop and mobile browser smoke for action visibility and horizontal overflow
- Live homepage and sitemap checks after deployment

## PageSpeed Mobile Evidence Loop

The PageSpeed Insights URL shared on 2026-06-02 showed that field data is not yet available for this young property, so mobile performance work must rely on repeatable lab evidence until Search Console and CrUX accumulate enough real-user samples.

Current project guard:

- `npm run seo:performance` runs mobile Lighthouse against `https://www.roth-conversion-calculator-ai.shop`.
- The command records `performance-evidence-result.json` with performance score, SEO score, LCP, TBT, CLS, Lighthouse version, final URL, and threshold metadata.
- The SEO Smoke workflow uploads the file inside the retained `production-seo-evidence` artifact.
- `npm run seo:evidence-validate` verifies that mobile Lighthouse evidence exists and that SEO remains above the hard threshold.
- Performance score, LCP, TBT, and CLS threshold misses are retained as `manualReviewRequired` evidence instead of blocking CI, because GitHub-hosted Lighthouse runners have shown high metric variance.

Current conservative review thresholds:

- Mobile Lighthouse performance score: at least `0.50` as a review signal, with `0.75+` as the next optimization target.
- Mobile Lighthouse SEO score: at least `0.95`.
- Largest Contentful Paint: at most `5000ms`.
- Total Blocking Time: at most `600ms` as a review signal, with `<300ms` as the next optimization target.
- Cumulative Layout Shift: at most `0.1`.

Mobile paint simplification on 2026-06-02:

- Small-screen viewports now use a simple linear background instead of the desktop radial-plus-linear layered background.
- Desktop keeps the existing visual treatment.
- The goal is to reduce mobile first-paint and LCP rendering work without changing calculator copy, layout hierarchy, schema, or YMYL boundaries.
- `tests/core/homepage-performance.test.ts` guards that the small-screen background path does not reintroduce `radial-gradient`.

Mobile glass-effect reduction on 2026-06-02:

- Shared `Card` surfaces now use `shadow-sm` and `backdrop-blur-none` on mobile, then restore `shadow-material` and `backdrop-blur-xl` from the `sm` breakpoint.
- The homepage primary navigation follows the same pattern: lighter mobile paint, desktop glass treatment preserved.
- This keeps the calculator input/results hierarchy intact while reducing expensive backdrop-filter work near the first paint.
- `tests/core/homepage-performance.test.ts` guards the mobile/desktop class split for the shared card surface and primary navigation.

Mobile calculator-first layout on 2026-06-02:

- The homepage workflow explainer cards now render after `HomeCalculatorClient`.
- This lets mobile users reach the calculator input and result surface before the three-step explainer cards.
- The workflow copy remains visible and crawlable, but it no longer competes with the first calculation surface on small screens.
- `tests/core/homepage-performance.test.ts` guards that `HomeCalculatorClient` stays before the `AI calculator workflow` section in source order.

Mobile result density refinement on 2026-06-02:

- The result action buttons now render after `ResultSummary`, so mobile users see the core estimate before share, report, CPA packet, and reset controls.
- `ResultSummary` uses smaller mobile padding, `text-2xl` primary values, and desktop-only explanatory footnotes on the three primary estimate cards.
- Scenario reading and secondary amount cards keep their content visible with tighter mobile spacing.
- `tests/core/homepage-performance.test.ts` and `tests/core/result-actions-layout.test.ts` guard the result-before-actions order and compact mobile classes.

Performance review trigger evidence on 2026-06-02:

- `performance-evidence-result.json` now includes `reviewTriggers` when a Lighthouse threshold misses.
- The retained evidence also includes `reviewSummary` so operators can see whether the review was caused by TBT, LCP, CLS, SEO score, or overall performance score.
- This preserves GitHub runner variance as evidence before changing production UX, especially when local production Lighthouse remains healthy.
- `tests/core/performance-evidence.test.ts` guards the new diagnostic fields.

TBT attribution diagnostics on 2026-06-02:

- `performance-evidence-result.json` now includes `tbtDiagnostics`.
- The diagnostic block retains compact top lists for Lighthouse `long-tasks`, `mainthread-work-breakdown`, `bootup-time`, and `third-party-summary`.
- The goal is to separate production page work from lab-runner variance before changing calculator UX or thresholds.
- `scripts/validate-seo-evidence.mjs` now requires those diagnostic arrays in retained production evidence artifacts.

Lazy GA4 loading on 2026-06-02:

- GA4 loader and config scripts now use the Next.js `lazyOnload` strategy.
- Analytics remains enabled and privacy-safe, but the external Google tag no longer competes with the calculator's first interactive path.
- Calculator analytics events still use bucketed values and avoid exact financial inputs.
- `tests/core/analytics.test.ts` guards that GA4 does not regress to `afterInteractive`.

Deferred GA4 idle loader on 2026-06-02:

- The GA4 integration now renders a small inline dataLayer/gtag queue and defers external `gtag.js` injection until after page load and browser idle time.
- A short fallback timer still loads analytics if idle callbacks are unavailable, preserving GA4 collection while moving third-party work away from the first interactive path.
- Calculator result events continue to queue through `window.gtag` and retain bucketed, non-exact financial values.
- `tests/core/analytics.test.ts` guards the deferred loader, load listener, idle callback, and removal of `next/script` for GA4.

First-party TBT attribution on 2026-06-02:

- `performance-evidence-result.json` now includes `tbtDiagnostics.attributionSummary`.
- The summary groups long-task and script-bootup duration by `homepageDocument`, `nextChunk`, `firstPartyOther`, `thirdParty`, `unattributable`, or `unknown`.
- This makes the next optimization decision evidence-led after third-party GA4 work was moved out of the measured long-task window.
- `scripts/validate-seo-evidence.mjs` requires the attribution summary in retained production artifacts.

Median Lighthouse performance evidence on 2026-06-02:

- `seo:performance` now collects up to three mobile Lighthouse samples by default.
- Each attempt is retained in `samplePolicy.attempts`, including invalid samples such as transient null SEO categories.
- The retained evidence selects the valid median TBT sample with `selectionStrategy: median-total-blocking-time-valid-seo-sample`.
- This reduces overreaction to isolated GitHub runner variance while still preserving every sampled result for review.
- `PERFORMANCE_EVIDENCE_SAMPLE_COUNT` can tune the sample count from 1 to 5 for local or CI diagnostics.
- `scripts/validate-seo-evidence.mjs` requires `samplePolicy` so retained artifacts remain self-describing.

Performance audit sample policy visibility on 2026-06-02:

- `/performance-audit` now includes a release regression check for multi-sample Lighthouse evidence.
- Operators should confirm `samplePolicy.attempts` retains every attempt, `validSamples` is at least 1, and the selection strategy is `median-total-blocking-time-valid-seo-sample`.
- This keeps the visible operations playbook aligned with the retained GitHub Actions production evidence artifact.

Lighthouse warning classification on 2026-06-02:

- `performance-evidence-result.json` now includes `warningClassification`.
- Each sample attempt also includes `warningClassification`, and `samplePolicy.warningSummary` gives a compact per-attempt view.
- Chrome launcher temporary-directory cleanup warnings are classified as `chrome-temp-cleanup-warning` with `blocking: false` when a valid Lighthouse report was produced.
- Other Lighthouse runtime warnings remain `runtime-warning` with `blocking: true` so they still require review.

Next optimization target:

- Reduce mobile LCP before tightening the threshold below `5000ms`.
- Convert performance review signals into CI-blocking thresholds only after GitHub runner evidence is consistently stable.
- Keep YMYL copy, schema, and calculator behavior unchanged while optimizing render path.

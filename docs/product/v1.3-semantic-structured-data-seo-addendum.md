## High-Risk Instructions That Must Not Be Copied Directly

Some instructions in the source documents are useful as intent, but unsafe or inaccurate as literal implementation.

### 1. Do Not Replace the HTML Skeleton

The documents describe replacing `index.html`. This project is a Next.js app router project, not a single static `index.html` app.

Decision:

- Do not replace the root HTML skeleton manually.
- Use Next.js `metadata`, `viewport`, route components, and JSON-LD scripts.
- Preserve hydration, routing, dynamic imports, analytics boundaries, and calculator state.

### 2. Do Not Use Unsafe YMYL Claims

The documents repeatedly use phrases such as:

- `optimal amount`
- `hidden fees`
- `100% private`
- `accurate results`
- `lifetime tax savings`
- `recommendations`

Decision:

- Public copy must stay educational and assumption-based.
- Use `modeled estimate`, `review items`, `tax interaction warnings`, and `professional review`.
- Avoid any phrase that implies personalized advice, guaranteed accuracy, or a best conversion amount.

### 3. Do Not Add Fake Ratings or Reviews

The documents propose `aggregateRating` with a 4.9 rating and 1,247 reviews. No visible, verified review corpus exists in the current product.

Decision:

- Do not add `aggregateRating`, `review`, or star-rating markup unless real user reviews are visible on the page and governed by a review policy.
- Fake or unsupported ratings create structured-data spam and trust risk.

### 4. Do Not Promise Rich Results or CTR Gains

The documents claim rich media display and very large CTR gains. Google does not guarantee rich results even when structured data validates.

Decision:

- Treat structured data as a machine-readable clarity layer.
- Do not promise rich snippets, calculator cards, star ratings, or a fixed CTR lift.

### 5. Do Not Mark Unsupported Features

The documents mention voice input, voice output, hidden-fee calculation, and accessibility features that are not implemented as product features.

Decision:

- Do not include unsupported `accessibilityFeature`, `featureList`, or schema fields.
- Structured data must reflect visible, working product behavior.

### 6. Reframe FAQ and HowTo Expectations

FAQ and HowTo markup may still help machines understand content, but they should not be treated as guaranteed Google rich-result opportunities.

Decision:

- Keep FAQ JSON-LD only when the FAQ content is visible on the page.
- Do not describe FAQ markup as a rich-result growth lever for this tax calculator.
- Keep HowTo JSON-LD educational and visible, with no personalized action instruction.

## Official Guidance Applied

Implementation should follow current Google guidance:

- General structured data guidelines: structured data must represent visible page content, must not be misleading, and fake reviews can create manual-action risk.
  Source: https://developers.google.com/search/docs/appearance/structured-data/sd-policies
- Google recommends JSON-LD and notes that valid structured data does not guarantee rich results.
  Source: https://developers.google.com/search/docs/appearance/structured-data/intro-structured-data
- FAQ rich results stopped appearing in Google Search as of May 7, 2026, with remaining eligibility limited to well-known authoritative government or health sites.
  Source: https://developers.google.com/search/docs/appearance/structured-data/faqpage
- Software application structured data can describe software app pages, but review and aggregate-rating fields must follow review-snippet rules.
  Source: https://developers.google.com/search/docs/appearance/structured-data/software-app
- AI features in Google Search do not require special schema.org markup; normal SEO fundamentals still matter.
  Source: https://developers.google.com/search/docs/appearance/ai-overviews

## Recommended Engineering Direction

### P1: Safe Homepage Structured Data Graph

Add or refine homepage JSON-LD only where it reflects visible content:

- `WebApplication` or `SoftwareApplication`
- `Organization`
- `WebPage`
- `BreadcrumbList`
- `HowTo` if all steps are visible on the page
- `FAQPage` only for visible FAQ content, without promising rich-result display

Rules:

- Use `@id` to connect graph nodes.
- Use the official canonical host: `https://www.roth-conversion-calculator-ai.shop`.
- Do not add `aggregateRating` or `review`.
- Do not include unsupported voice features.
- Do not include `Calculator` as the main Google rich-result strategy unless validation confirms it adds value without errors.

### P1: Structured Data Guard Tests

Add tests before expanding schema:

- JSON-LD uses the `www` canonical host.
- No JSON-LD includes `aggregateRating` or `review` without a visible review source.
- No JSON-LD contains `optimal conversion amount`, `hidden fees`, `guaranteed`, or `100% accurate`.
- Homepage structured data names and descriptions match visible homepage content.
- All JSON-LD objects parse cleanly.

### P2: Semantic HTML Audit

Audit existing homepage landmarks without rewriting the app:

- One visible `h1`.
- One `main`.
- Header and nav have clear labels.
- Calculator input controls have label-to-input association.
- Result sections use headings that describe content accurately.
- Footer links are crawlable and not stuffed.

### P2: SEO Copy Alignment

The source documents request 300 words of bottom-page content. The current homepage already includes methodology, source, FAQ, internal links, and disclaimer content.

If adding more copy:

- Keep it visible and useful to users.
- Avoid keyword-stuffed repetition.
- Explain what the calculator models, what it does not model, and when professional review is needed.
- Link to methodology, tax-data update, tax brackets, IRMAA, ACA, and CPA review pages.

### P3: Structured Data Evidence Command

Extend automation later with a dedicated structured-data evidence check:

- Fetch production homepage HTML.
- Extract `application/ld+json` scripts.
- Parse all JSON-LD.
- Check canonical host consistency.
- Check banned YMYL phrases.
- Check forbidden fake-review fields.
- Store the result in the `production-seo-evidence` artifact.

## Acceptance Criteria Before Implementation

- No calculator math, state, storage, analytics, AI, or UI behavior changes during semantic/SEO work.
- All metadata and structured data match visible page content.
- No unsupported features appear in schema.
- No fake review/rating markup.
- No public copy promises guaranteed rich results or fixed CTR lift.
- No public copy uses personalized recommendation language.
- `npm test`, `npm run build`, `npm run seo:smoke`, and `npm run seo:gsc-evidence` pass before deployment.

## Decision

Proceed with a conservative, evidence-backed SEO implementation path.

Do not copy the provided HTML and JSON-LD verbatim. Convert the documents into project-native Next.js metadata, visible semantic markup, source-aligned JSON-LD, and deterministic tests.

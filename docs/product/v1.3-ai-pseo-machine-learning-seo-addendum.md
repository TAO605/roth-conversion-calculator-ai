# V1.3 AI + PSEO Machine-Learning SEO Addendum

Date: 2026-06-15

## Purpose

This addendum evaluates the external document `20260412：AI + PSEO = 机器学习SEO.docx` and adapts it into the Roth Conversion Calculator engineering manual.

The document's strongest idea is not bulk AI publishing. The strongest idea is a feedback loop: use GA4, Search Console, and page-performance evidence to help AI learn which search intents, page patterns, and content decisions deserve more investment.

For this site, the implementation must stay compatible with Google people-first content guidance, Google Analytics Data API boundaries, and tax/YMYL compliance.

Official references checked:

- Google Search Central helpful, reliable, people-first content: `https://developers.google.com/search/docs/fundamentals/creating-helpful-content`
- Google Search Central SEO Starter Guide: `https://developers.google.com/search/docs/fundamentals/seo-starter-guide`
- Google Analytics Data API overview: `https://developers.google.com/analytics/devguides/reporting/data/v1`
- GA4 website/app setup help: `https://support.google.com/analytics/answer/9304153`

## Source Document Assessment

### What Is Useful

- It correctly separates publishing mechanics from the real problem: knowing whether pages are useful after publication.
- It identifies GA4 as a feedback input for page-level learning.
- It proposes weighted learning:
  - successful pages or search terms gain more weight,
  - weak pages lose weight,
  - high-performing page traits inform future topic ideas.
- It suggests a recurring learning cycle rather than one-time keyword research.

### What Needs Correction Before Engineering Use

- GA4 does not provide Google search query data by itself. Search query evidence should come from Google Search Console Performance exports or Search Console APIs. GA4 provides engagement and behavior signals after users land on the site.
- The document mentions downloading a Google service account JSON key. That key must never be committed to the repository, pasted into chat, stored in docs, or included in evidence artifacts.
- Nightly AI learning should not publish pages automatically on this YMYL tax site. It should create draft opportunities only.
- A raw success/failure multiplier such as `x1.1` or `x0.95` is useful as a mental model, but production scoring needs caps, confidence thresholds, sample-size requirements, and manual review states.
- Pattern learning must avoid copying competitor or prior page structure mechanically. It should identify intent gaps, useful evidence types, and internal-link opportunities.

## Safe AI + PSEO Operating Model

Use this loop:

1. Observe
   - Import Search Console queries and pages when available.
   - Import GA4 landing-page engagement when an approved API connection exists.
   - Keep all raw private exports local or sanitized before committing.

2. Cluster
   - Group keywords by search intent, not by exact keyword.
   - Merge variants such as `roth conversion calculator`, `roth ira conversion calculator`, and `2026 roth conversion calculator` when they serve the same page intent.

3. Score
   - Score pages and opportunities using conservative, capped weights.
   - Require minimum impressions, clicks, or engaged sessions before treating a signal as meaningful.
   - Treat very low sample size as `insufficient evidence`, not failure.

4. Decide
   - Choose one safe action:
     - refine homepage/result copy,
     - improve an existing guide,
     - add internal links,
     - create a new educational page,
     - update a source/methodology page,
     - add the idea to backlog,
     - reject because it is too personalized or too risky.

5. Draft
   - AI may draft outlines, snippets, or engineering tickets.
   - AI must not publish final YMYL article copy without the owner review boundary already defined in the blog workflow.

6. Validate
   - Run content readiness checks.
   - Run YMYL language guards.
   - Check official sources for tax, Medicare, ACA, Social Security, state tax, NIIT, AMT, RMD, and IRS-form claims.
   - Confirm structured data represents visible content.

7. Publish Gate
   - Only after owner approval and engineering validation.
   - Production deployment remains behind explicit confirmation.

8. Learn
   - After publication or refresh, compare later GSC/GA4 evidence against the prior baseline.
   - Update scoring history without overwriting the prior decision record.

## PSEO Scoring Proposal

Do not use a simplistic traffic-only score. Use a bounded score with confidence:

```text
opportunityScore =
  searchDemandScore
  + engagementScore
  + businessFitScore
  + contentGapScore
  + internalLinkScore
  - ymylRiskPenalty
  - thinContentPenalty
  - cannibalizationPenalty
```

Recommended inputs:

- Search Console:
  - impressions,
  - clicks,
  - CTR,
  - average position,
  - query/page pairing,
  - trend compared with prior period.
- GA4:
  - landing-page sessions,
  - engaged sessions,
  - engagement rate,
  - average engagement time,
  - scroll or calculator interaction events when privacy-safe,
  - return visits where available and non-identifying.
- Site evidence:
  - whether a matching page exists,
  - internal-link depth,
  - sitemap/llms inclusion,
  - structured-data type,
  - source freshness,
  - YMYL risk level.

Minimum confidence rules:

- If impressions and sessions are both low, mark as `insufficient evidence`.
- If clicks are low but impressions are rising, prefer snippet/title/meta improvement before new page creation.
- If engagement is low, inspect page intent mismatch before publishing more related pages.
- If a query asks for personalized tax advice, use an educational guide or calculator explanation boundary instead of a recommendation page.

## Automation Boundaries

Allowed autonomous actions:

- Import sanitized CSV exports.
- Generate draft opportunity records.
- Score existing pages.
- Propose internal-link changes.
- Propose refresh tickets.
- Update local engineering documentation.
- Run tests, build, SEO smoke, and evidence validators.

Blocked without explicit approval:

- Creating a Google Cloud project.
- Enabling APIs in a Google account.
- Creating or downloading service account JSON keys.
- Adding a service account to GA4.
- Storing credentials in local files or environment variables.
- Publishing pages to production.
- Changing DNS, Search Console ownership, GA4 admin settings, or billing/spend.

Always prohibited:

- Committing service account JSON keys.
- Pasting private API keys, cookies, tokens, or GA4 account screenshots into docs.
- Auto-publishing AI-written YMYL content.
- Creating doorway pages, keyword-stuffed pages, or one page per trivial query variant.
- Faking freshness, ratings, reviews, expert review, or tax-professional approval.

- Output path is local draft evidence.

### P1A: GA4 CSV Data Quality Gate

Before any GA4 export is used for AI+pSEO decisions, run a local CSV audit:

```bash
npm run seo:ga4-report-audit -- "C:\path\to\GA4-overview-export.csv"
```

The audit must classify the export as `usable`, `needs-review`, or `polluted` before engagement metrics are trusted.

The gate checks:

- foreign or unrelated page titles, such as another site's brand or product pages;
- unknown page titles that need a `Hostname` dimension review;
- separate first-user and session acquisition sections without double-counting them;
- Chinese Roth Calculator titles as site-relevant instead of unknown, so multilingual project pages do not create false alarms;
- very low average engagement time that may indicate bots, owner testing, or accidental traffic;
- low Google organic sample size;
- direct traffic domination that can distort SEO scoring.

If unrelated page titles appear, do not use the export for pSEO scoring. First review GA4 with the `Hostname` dimension. If another domain is sending events to this Measurement ID, remove the ID from that site or move Roth Calculator to a clean GA4 property. This is a data-quality repair, not a content decision.

Recommended manual GA4 follow-up:

1. Open GA4 Reports or Explore.
2. Add `Hostname` as a dimension.
3. If `Hostname` is not available in the Explore picker, add `Page location` / `网页位置` and extract the hostname from the full URL.
4. Compare hostnames against `www.roth-conversion-calculator-ai.shop` and `roth-conversion-calculator-ai.shop`.
5. Treat `127.0.0.1` or `localhost` as local development traffic, not an external site, but keep it out of production SEO scoring.
6. If another hostname appears with the same page titles, treat the property as polluted until the Measurement ID is removed from that site or the Roth Calculator site is moved to a clean property.
7. Export the hostname or page-location report and run this audit again before using GA4 data in the AI+pSEO backlog.

When a Hostname or Page location CSV is available, run the dedicated hostname audit:

```bash
npm run seo:ga4-hostname-audit -- "C:\path\to\GA4-hostname-export.csv"
```

The hostname audit is stricter than the page-title audit. It is `usable` only when all non-local rows belong to `www.roth-conversion-calculator-ai.shop` or `roth-conversion-calculator-ai.shop`. Any other hostname means the GA4 property remains polluted and must not feed the AI+pSEO scoring loop. Local development rows such as `127.0.0.1` are reported separately as a cleanup item.

Create a command:

```bash
npm run seo:ga4-pseo-import -- --start YYYY-MM-DD --end YYYY-MM-DD --output tmp-ga4-pseo-pages.json
```

The importer should read:

- landing page path,
- sessions,
- engaged sessions,
- engagement rate,
- average engagement time,
- key privacy-safe calculator events if already implemented.

The importer should not:

- store service account JSON,
- request user-level dimensions,
- request demographic or sensitive dimensions,
- publish decisions directly.

### P3: Unified PSEO Opportunity Engine

Create a draft-only engine that combines:

- GSC query opportunity records,
- GA4 landing-page engagement records,
- site index route inventory,
- blog readiness rules,
- YMYL risk taxonomy.

Output:

```text
docs/seo-opportunities/YYYY-MM-DD-pseo-backlog.json
```

Each record should include:

- intent cluster,
- affected URL,
- evidence summary,
- score,
- confidence,
- recommended action,
- review gate,
- rejection reason if blocked,
- next validation command.

### P4: Content Refresh Workflow

For existing pages, prefer refresh actions before new pages:

- update page title or meta only if query intent and page content already match,
- add missing FAQ-like explanatory subsection only when visible on page and not mounted as fake FAQ structured data,
- add internal links from relevant guide/hub pages,
- add source freshness notes,
- update comparison tables or examples,
- add calculator anchor/prefill link when useful.

### P5: New Page Creation Gate

New PSEO pages are allowed only when:

- the intent is distinct,
- the topic is not covered by an existing page,
- the page can provide original calculator-specific value,
- official sources exist,
- YMYL risk is handled,
- sitemap/site-index/llms/internal links are planned,
- tests are added.

## Acceptance Criteria

- PSEO decisions are based on evidence, not blind AI content generation.
- GA4 is used for aggregate engagement, while Search Console is used for query evidence.
- Low-sample data cannot trigger publication.
- YMYL-sensitive topics route to review gates.
- AI can generate drafts and tickets, but not publish final YMYL pages by itself.
- Credential handling is explicit and safe.
- Homepage remains tool-first.
- Every future PSEO page or refresh has tests, build validation, SEO evidence, and post-deploy verification.

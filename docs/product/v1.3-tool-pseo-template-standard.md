# Tool pSEO Single-Page Template Standard

Date: 2026-06-21

## Assessment First

The submitted single-page tool template is directionally useful because it matches the premium tool-page model:

`tool page + landing page + result display page = premium tool page`

However, it must not be copied into production as a mass-generation shortcut. For Google SEO and YMYL safety, the template is approved only as a controlled page pattern with quality gates.

Accepted:

- Semantic page structure with one H1, crawlable copy, visible tool entry, visible sample result, trust/source area, FAQ, and internal links.
- Template variables for metadata, tool parameters, calculation rules, sample result, source, FAQ, and related links.
- One primary keyword/search intent per canonical URL.
- Batch-generation readiness only when every page has real user value and unique intent.

Corrected before adoption:

- Do not use unsupported or unsafe `Calculator` rich-result claims. Use `WebApplication` and `WebPage` instead.
- Do not show `reviewedBy` unless a real professional reviewer exists.
- Do not create fake ratings, fake reviews, fake freshness, fake credentials, or unsupported accuracy claims.
- Do not treat variable count as quality by itself. A page can have 35 variables and still be thin or doorway-like.
- Do not rely on keyword density as a ranking hack. Use keywords naturally in title, H1/H2, intro, body, and closing where it helps the reader.

Approved template:

## Google-Aligned Boundary

This standard follows these Google-safe boundaries:

- Pages must be made for people-first tool intent, not only search manipulation.
- Programmatic pages must not become scaled low-value pages.
- Structured data must match visible page content.
- FAQ structured data is allowed only when the same Q&A is visible on the page.
- User-generated or private-result pages should default to `noindex` unless they pass a public-quality review gate.
- Public pages should be crawlable and useful without forcing immediate login.

Primary references:

- Google helpful content: `https://developers.google.com/search/docs/fundamentals/creating-helpful-content`
- Google spam policies and scaled content abuse: `https://developers.google.com/search/docs/essentials/spam-policies`
- Google structured data guidelines: `https://developers.google.com/search/docs/appearance/structured-data/sd-policies`

## Variable Requirement Matrix

| Module | Variable Count | Required | Standard |
| --- | ---: | --- | --- |
| Metadata + Schema | 12+ | Yes | Title, description, canonical, WebApplication, WebPage, Breadcrumb fields must be unique per indexable page. |
| First-Screen Tool Area | 5+ | Yes | H1, intro, tool component, default parameters, and calculation logic must match the keyword intent. |
| Sample Result Area | 8+ | Yes | Each page needs a distinct sample scenario and visible result preview. |
| Deep Content Area | 12+ | Yes | Tutorial, use cases, and calculation rules should be at least 60% unique by page. |
| Trust Area | 6 | Partial | Source and update date are required when rules/data are used; reviewer fields appear only when real. |
| FAQ Area | 6 | Conditional | Use only when visible FAQ exists; at least 2 page-specific questions. |
| Internal Links | 12 | Dynamic | At least 3 contextual internal links; avoid orphan pages. |

The template has more than 35 variable slots and satisfies the minimum 15-variable safety threshold. This is a minimum engineering threshold, not an SEO guarantee.

## Batch Generation Must-Pass Checklist

Every generated page must pass before it is indexable:

- Title, description, and canonical are 100% unique.
- Title formula targets 50-60 characters when natural. For long-tail YMYL tool pages, clarity and exact intent may justify a longer title; the quality gate reports this as a warning rather than forcing keyword loss.
- Meta descriptions should usually stay within 120-160 characters, with 150-160 preferred when natural and readable.
- One primary keyword/search intent maps to one canonical page.
- Tool component parameters, default values, assumptions, and calculation rules are differentiated; no site-wide identical widget with swapped keywords.
- Visible body content is at least 60% unique; shared boilerplate stays below 40%.
- Each page must keep at least 15 meaningful variable slots across metadata, intent, sample scenario, assumptions, FAQ, result focus, and trust/disclaimer fields.
- Sample result values, labels, and explanations are page-specific.
- Schema fields correspond to visible page content.
- No fake reviewer, fake rating, fake review count, fake date freshness, or unsupported authority claim.
- Related calculator recommendations should render 4-6 relevant internal links when enough sibling pages exist; at least 3 relevant internal links remain the minimum for small clusters.
- FAQ blocks should include 3-5 visible questions per page, with matching FAQ structured data generated from the same source fields.
- No orphan pages.
- Mobile layout renders without horizontal overflow.
- The tool component is fully usable on mobile.
- Images, if present, have descriptive `alt` text.
- External links use `rel="nofollow noopener noreferrer"` when following the project rule.
- FAQ schema appears only when the visible FAQ block exists.
- Indexable pages include crawlable explanatory copy, not only a widget.

If a page fails one of these gates, it should remain unpublished, stay in draft, or use `noindex` until repaired.

Current project guard:

```bash
npm run seo:pseo-batch-quality-gate -- --out pseo-batch-quality-gate-result.json
```

This guard checks the current keyword landing-page source, route template, and sitemap registration for:

- Unique title, description, slug, keyword, and canonical path signals.
- Differentiated sample scenarios and assumptions.
- Minimum variable-slot coverage.
- Visible FAQ content and matching FAQ structured data.
- Visible calculated sample result preview.
- Four related internal calculator recommendations for the current 8-page cluster.
- Sitemap coverage.
- No fake reviewer, rating, or authority schema in keyword landing pages.
- No YMYL overclaims such as guaranteed accuracy or optimal conversion advice.
- External-link `rel` safety when external links exist in the template.

## Content Rules

For tool pages and articles:

- The primary keyword should appear naturally in the title, H1, at least one H2 when appropriate, the first 100 words, and the final 100 words.
- Page text should be long enough to satisfy the task. For tool pages, useful content and tool value matter more than word count. For blog articles, 800+ words is the minimum target and 1500+ words is preferred when the topic needs depth.
- Keyword density should be treated as an editorial warning signal, not a mechanical target. Avoid stuffing. If a 2%-4% target makes the copy awkward, reduce it.
- One page has one H1. H2 headings form the main outline. H3/H4 headings are used for subtopics.
- Body text uses normal paragraph tags. Important terms can be bolded sparingly.
- Copy must be fluent English, grammar-checked, typo-free, and manually reviewed before publication.

## YMYL Rules For Roth Conversion Pages

For Roth conversion, tax, retirement, Medicare, ACA, Social Security, NIIT, AMT, RMD, or state-tax pages:

- Use educational, assumption-based wording.
- Do not claim final tax-return accuracy.
- Do not provide personalized recommendations.
- Do not say the calculator determines the best or optimal conversion amount.
- Include a professional-review boundary.
- Link to official sources when citing tax or government rules.
- Use bounded previews or worksheets when a complete tax-form engine is not implemented.

## Publication Workflow

1. Pick one primary keyword and one search intent.
2. Confirm the page is not cannibalizing an existing canonical page.
3. Fill all required metadata, tool, sample-result, content, trust, FAQ, and link variables.
4. Run uniqueness, template completeness, internal-link, mobile, and schema checks.
5. Confirm sitemap/canonical/robots coverage.
6. Run build and SEO smoke checks.
7. Deploy only after review and rollback path are clear.

## Current Project Fit

This standard fits the Roth Conversion Calculator site because:

- Existing tax-impact pages already follow the premium tool-page structure.
- Advanced pages use bounded previews and worksheets instead of unsafe final tax rulings.
- Future pSEO expansion should begin with a small set of researched low-competition tax-impact tool pages, not mass pages.
- GSC and GA4 should guide future page clusters only after data is clean and stable.

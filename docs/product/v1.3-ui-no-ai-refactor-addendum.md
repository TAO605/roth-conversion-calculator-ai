## Assessment

The source document is directionally useful for removing low-trust template styling from the calculator UI, but it assumes a single-file `index.html` implementation. The live product is a Next.js SEO application with structured data, guide pages, analytics, Search Console evidence, release notes, tests, and Vercel/GitHub deployment automation.

Therefore this document is accepted as a visual refactor brief, not as an instruction to replace the application architecture.

## Safe Adaptation

Non-negotiables:

- Do not change Roth conversion calculation logic.
- Do not remove homepage JSON-LD, canonical SEO metadata, sitemap, robots, GA4, GSC verification, or evidence workflows.
- Do not remove the AI explainer feature; demote AI from the brand/hero hierarchy and keep it as a low-hierarchy explanation surface.
- Do not claim tax advice, optimal conversion amounts, guaranteed accuracy, or personalized recommendations.
- Keep all original inputs available, including advanced assumptions and state shortcut examples.

Accepted visual direction:

- Replace glass, blur, glow, heavy shadows, large rounded corners, and translucent panels with plain white/bordered financial-tool surfaces.
- Use a restrained primary navy (`#0A2463`), neutral borders, existing success/danger colors, and monospace numeric values.
- Make the calculator feel like a professional planning worksheet rather than an AI landing page.
- Keep mobile first-screen density and performance gains from previous rounds.

## Execution Plan

P1 homepage/core calculator surface:

- Shared `Card`, `Button`, and `Field` primitives use plain borders, 4px radius, no shadows, no glass/blur, and tighter focus rings.
- Homepage hero uses `Roth Conversion Calculator 2026` and `2026 tax estimate` instead of AI-first brand copy.
- Calculator input/result layout uses a 40/60 desktop split (`lg:grid-cols-5`, input `lg:col-span-2`, result `lg:col-span-3`).
- Quick Estimate, Advanced assumptions, presets, result cards, and advanced details use plain bordered surfaces.
- Primary result numbers use monospace 32px bold styling.

P2 supporting calculator panels:

- Review AI explainer, tax warnings, projection, payment comparison, and detailed breakdown for leftover glass or decorative treatment.
- Preserve their current placement and compliance wording.
- Demote the explainer from AI-first visible labels to a low-hierarchy educational explanation assistant.
- Use plain bordered surfaces for tax impact warnings, payment comparison, projection chart, calculation breakdown, and scope badges.
- Keep warning semantics through copy, icons, and border color rather than large tinted panels or shadows.
- Use monospace numeric emphasis in supporting result panels where projected values or formula outputs are shown.

P3 operations/content pages:

- Review long-form operational pages only after homepage calculator UI stabilizes.
- Keep content pages readable and SEO-aligned; do not chase a sitewide visual rewrite in one release.

P3 homepage detail polish:

- Keep result actions visually stable while lazy-loaded report and CPA packet modules hydrate.
- Use disabled, size-stable placeholders for lazy action buttons instead of returning `null`.
- Keep the action toolbar on a predictable two-column mobile grid and four-column desktop grid.
- Preserve the current result order: scope badges, primary estimates, secondary actions, warnings, payment comparison.
- Do not change calculation logic, report contents, CPA packet contents, or YMYL/compliance language.

P4 mobile input density:

- Keep the first Quick Estimate view focused on conversion amount, current taxable income, filing status, state marginal tax rate, and traditional IRA balance.
- Move projection-only assumptions such as retirement age and expected annual return into a collapsed `Projection assumptions` disclosure inside Quick Estimate.
- Keep projection assumptions available without moving them into the separate Advanced assumptions block.
- Preserve default values and calculation behavior; this is a disclosure and density change, not a model change.
- Keep all original inputs available and avoid hiding YMYL boundary copy or validation errors.

P5 disclosure interaction polish:

- Keep `Projection assumptions` and `Advanced assumptions` as native `<details>/<summary>` disclosures.
- Make summary rows at least 44px tall for mobile touch comfort.
- Use a visible chevron affordance that rotates on open state.
- Hide default browser disclosure markers only when the custom chevron remains visible.
- Preserve keyboard and screen-reader behavior by avoiding custom JavaScript toggles.

P6 operations/content page surfaces:

- Start the broader operations/content-page cleanup with audit and playbook routes rather than blog/article bodies.
- Replace glass, blur, large-radius, translucent, and heavy-shadow containers with plain bordered review panels.
- Keep operational pages dense, calm, and scannable; they should feel like audit worksheets, not marketing sections.
- Preserve all existing SEO metadata, JSON-LD breadcrumbs, disclaimer text, source links, and review workflow copy.
- Add a regression guard that scans the operations routes for old template surface classes.

P7 top-level content hub surfaces:

- Continue the broader content-page cleanup with index and hub pages before editing article or guide bodies.
- Replace translucent, large-radius, hover-lift, and heavy-shadow link cards with plain bordered navigation panels.
- Keep hub pages scannable as internal-link and crawl-orientation surfaces, not decorative landing pages.
- Preserve hub metadata, JSON-LD breadcrumbs, disclaimers, routes, and link targets.
- Add a regression guard that scans top-level hub routes for old template card classes.

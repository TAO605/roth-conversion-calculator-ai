# Premium Tool Page pSEO Execution Plan

Date: 2026-06-16

## Executive Decision

The site should use a tool-led pSEO model, but only with review-gated, people-first pages. The updated working formula is:

1. One keyword = one page.
2. Tool page + landing page + result display page = premium tool page.
3. Premium tool page + low-competition long-tail keyword = ranking and impression opportunity.
4. Unified public/tool URL + task-completion behavior data = enough page-level learning signal in one place.
5. Ranking and impressions + useful task completion signals = higher probability of stronger search performance over time.

The behavior-data formulas are growth hypotheses, not guaranteed Google ranking rules. Google Search work must still follow helpful, reliable, people-first content principles and help search engines understand the page without creating doorway, duplicate, thin, or scaled low-value pages.

## Product Fit

This model fits the Roth Conversion Calculator because users have many recurring, specific, calculator-shaped intents:

- How much tax will a Roth conversion create?
- How much can I convert without entering a higher bracket?
- Will IRMAA change?
- Will ACA premium tax credit exposure change?
- Will Social Security taxable benefits change?
- What happens in a state such as CA, NY, NJ, TX, or FL?
- Is a staged conversion different from a lump-sum conversion?

The site should not split SEO value across `www` content and an `app` subdomain. The main-domain page should contain the crawlable explanation, the tool entry, and the result/example value.

When the same user task can be served before and after login, prefer one canonical URL. The logged-out state should expose crawlable landing copy, the tool entry, and safe examples; the logged-in state may reduce marketing copy and focus on the working interface without changing the core URL. This keeps page-level analytics, task completion, internal links, and search intent aligned.

## Premium Tool Page Acceptance Criteria

Each new long-tail page must have one primary keyword and one clear search intent.

Required page elements:

- Server-rendered H1 and metadata that match the primary intent.
- Crawlable landing copy that explains the problem, who the page is for, and what the calculator can and cannot do.
- A tool entry path, preferably a prefilled calculator link or embedded tool section.
- A result display section with one or more fixed sample scenarios, not private user data.
- Visible YMYL boundaries: educational estimate, not tax/legal/financial advice, not a final tax return.
- Internal links to the main calculator, methodology, tax data, professional review packet, and related guides.
- Sitemap inclusion, canonical URL, and structured-data evidence where appropriate.
- No keyword stuffing, fake freshness, copied boilerplate, or pages that differ only by swapped keywords.

## Generated Result Pages And Whitelist Aggregation

Do not index every user-generated result, prompt, scenario, or saved output page by default.

For any future generated-result system:

- Default generated/private/user-specific pages to `noindex` unless they pass a reviewed public-quality gate.
- Do not put private user inputs, personal financial facts, or saved scenarios into indexable pages.
- Use canonical URLs for duplicate or near-duplicate public pages.
- Create indexable tag, collection, or keyword pages only from a whitelist of searched, useful intents.
- Each indexable collection page must include original crawlable copy, a real tool entry, curated or representative result examples, internal links, and a clear reason it deserves to exist.
- Similar long-tail variants should consolidate into one stronger page unless the user task is meaningfully different.
- New domains should avoid large-scale page generation. Start with a small reviewed set, prove indexing and user value, then expand gradually.

For this Roth Conversion Calculator site, generated individual user scenarios should remain local/browser-only or non-indexable. Indexable expansion should happen through reviewed calculator pages such as tax interaction, state, tax bracket, and planning pages.

## User Behavior Data Boundary

Useful behavior data for the project means aggregate, consent-safe signals such as:

- Search Console impressions, clicks, CTR, and average position.
- GA4 aggregate engagement after host pollution is removed.
- Calculator starts, completed estimates, report downloads, share actions, and professional packet actions.
- Return visits or internal navigation patterns at aggregate level.

Do not collect or store private tax inputs for SEO learning. Do not send personal financial inputs, emails, notes, API keys, cookies, or exact saved scenarios into analytics or AI scoring.

Interpret behavior data as product feedback and prioritization evidence. Do not claim that bounce rate, dwell time, or pageviews directly guarantee a Google ranking position.

## Practical Execution Workflow

The execution should stay incremental and evidence-driven:

1. Keep the homepage as the primary tool experience.
2. Upgrade existing long-tail keyword pages before creating new pages.
3. For each page, combine crawlable landing copy, a direct calculator entry, and a fixed sample result preview on the same URL.
4. Keep public/tool behavior on the same canonical URL when login is not required.
5. Run the premium tool-page validator before any publishing decision.
6. Use Search Console query exports and clean GA4 host data to choose the next page cluster.
7. Publish only pages with distinct user intent, distinct assumptions, and visible YMYL boundaries.

What AI can do without new user material:

- Improve page structure, internal links, sample result sections, metadata, validation scripts, and engineering documentation.
- Draft page outlines and first-pass copy for owner review.
- Build local tests and SEO guards.
- Analyze GSC and GA4 CSV exports when provided.

What the user should provide when available:

- Fresh GSC Performance CSV exports after the new pages have impressions.
- Fresh GA4 exports after `bobo-poolrobot.com` has disappeared from the Roth property data.
- Blog drafts if blog publishing resumes.
- A priority direction if there is a business preference: tax-bracket pages, tax-interaction pages, or state pages.

If the user does not choose a priority, the default next cluster is tax-interaction pages because it matches high-pain Roth conversion questions while reusing existing bounded worksheet logic:

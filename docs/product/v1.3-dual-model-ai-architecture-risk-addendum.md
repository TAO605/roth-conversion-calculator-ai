## Executive Evaluation

The dual-model AI direction is useful only if it is framed as a controlled educational explanation layer, not as an accuracy guarantee or tax-advice engine.

For a Roth conversion calculator, the phrase `zero hallucination + 100% accurate` is not acceptable as a public product promise. It creates YMYL compliance risk, Google trust risk, and product liability risk because:

- Tax outcomes depend on user-provided inputs, filing status, state assumptions, phaseouts, Medicare/ACA interactions, timing, and future law changes.
- AI-generated explanations can summarize, route, and cite model assumptions, but they cannot guarantee complete taxpayer-specific correctness.
- Even deterministic calculations can be accurate only under defined assumptions and reviewed tax data.
- Search and user trust improve when the site states limitations clearly instead of making absolute claims.

Recommended public framing:

- Use: `evidence-backed educational explanations`
- Use: `calculation-grounded AI summaries`
- Use: `source-aware review prompts`
- Use: `professional review recommended for personal tax decisions`
- Avoid: `zero hallucination`
- Avoid: `100% accurate`
- Avoid: `best conversion amount`
- Avoid: `you should convert`

## Architecture Boundary

The dual-model system should be a review-gated enhancement around the existing deterministic calculator.

Allowed responsibilities:

- Explain the already-computed result in plain English.
- Identify which assumptions were used.
- Cite internal methodology and tax-data source pages.
- Generate CPA review questions and document checklists.
- Compare user inputs against known warning triggers such as IRMAA, ACA, NIIT, RMD, Social Security, and state-tax assumption boundaries.
- Refuse personalized tax recommendations and route users to professional review.

Disallowed responsibilities:

- Invent tax rules not present in the deterministic rule engine.
- Override calculator outputs.
- Claim final tax owed for the taxpayer.
- Recommend a specific conversion amount as the best or optimal action.
- Estimate unsupported program effects without a rule engine and source review.
- Present AI output as tax, legal, investment, or financial advice.

## Proposed Dual-Model Pattern

Use a primary explainer model plus a verifier layer, but keep both downstream of deterministic calculation and compliance rules.

### 1. Deterministic Core

The calculator remains the source of truth for modeled values.

Required contract:

- Inputs are validated before calculation.
- Outputs include assumptions, tax year, filing status, state-tax assumption, and unsupported-interaction warnings.
- AI receives structured results, not raw free-form financial context unless required for the explanation.

### 2. Explainer Model

The explainer model converts structured calculator output into educational language.

Required controls:

- Prompt includes no-advice boundary.
- Prompt includes required disclaimer.
- Prompt forbids optimal-action phrasing.
- Prompt must cite internal pages or calculator fields used in the explanation.
- Output must be treated as draft text until verified.

### 3. Verifier Model or Verifier Function

The verifier checks whether the explanation stays inside allowed boundaries.

Preferred implementation order:

1. Deterministic verifier first: schema validation, banned phrase checks, citation presence, numeric consistency with calculator output, disclaimer presence.
2. LLM verifier second: classify whether the answer contains personal advice, unsupported claims, invented rules, missing uncertainty, or mismatch with the calculation payload.
3. Hard fallback: if verification fails, return a static safe explanation template instead of trying to repair live.

### 4. Evidence Log

Each AI response should be reviewable without storing sensitive user financial details.

Log only:

- Request type.
- Feature version.
- Tax year.
- Which safety checks passed or failed.
- Whether fallback was used.
- Non-sensitive error codes.

Do not log:

- Exact income.
- Exact conversion amount.
- Account balances.
- Personal identifiers.
- Full prompt content if it includes user financial inputs.

## Implementation Phases

### Phase A: Documentation and Guardrails

Status: recommended first.

Deliverables:

- This addendum.
- Updated AI compliance audit checklist.
- Tests that block absolute accuracy and advice language.
- A defined verifier result schema.

Exit criteria:

- Existing YMYL language guard covers public copy and AI fallback copy.
- Any public mention of dual-model AI uses educational, evidence-backed language.

### Phase B: Deterministic Verifier

Deliverables:

- `ai-response-verifier` module.
- Numeric consistency checks against calculator output.
- Citation and disclaimer checks.
- Banned phrase checks.
- Safe fallback templates.

Exit criteria:

- Unit tests prove unsafe AI text is blocked.
- The explainer cannot ship unverified text.

### Phase C: Optional Dual-Model Review

Deliverables:

- A verifier-model prompt with strict JSON output.
- Retry limit of zero or one; repeated failures return static fallback.
- Production telemetry for pass/fail/fallback counts only.

Exit criteria:

- LLM verifier never overrides deterministic verifier.
- No user-facing output claims guaranteed accuracy.

### Phase D: Search and Content Integration

Deliverables:

- `/ai-compliance-audit` updated with the dual-model review protocol.
- `/methodology` explains deterministic calculation vs AI explanation boundaries.
- `/seo-monitoring` treats AI-related pages as YMYL content requiring review gates.

Exit criteria:

- Production SEO smoke and YMYL guards pass.
- GSC content expansion remains educational and assumption-based.

## SEO Evaluation

The architecture can help SEO if it improves trust and task completion:

- Users get clearer result explanations.
- The site can answer long-tail intent without hiding the calculator.
- CPA handoff and methodology links strengthen E-E-A-T style trust signals.
- Safer AI language reduces thin or overclaiming content risk.

It can hurt SEO if implemented incorrectly:

- Absolute claims like `100% accurate` reduce trust for a tax tool.
- AI-generated pages without source review may be treated as low-quality or risky YMYL content.
- Personalized recommendation copy can create compliance and ranking risk.
- Unsupported tax-interaction estimates may increase user complaints and pogo-sticking.

SEO rule:

AI may improve clarity, not authority. Authority must come from deterministic calculations, source links, methodology, review dates, and professional-review boundaries.

## Required Tests Before Development

- Public copy must not contain `zero hallucination`, `100% accurate`, `guaranteed`, `best amount`, or `should convert`.
- AI output verifier rejects:
  - personalized recommendations,
  - unsupported tax claims,
  - numbers that do not match the deterministic result,
  - missing disclaimer,
  - missing assumption/citation references.
- Fallback response renders when verifier fails.
- No exact financial inputs are sent to analytics or retained in logs.
- Production `npm run seo:smoke` and `npm run seo:gsc-evidence` remain green after deployment.

## Decision

Proceed only as a phased, verifier-gated AI explanation system.

Do not proceed with any public or internal implementation that treats dual-model AI as a guarantee of zero hallucination or 100% tax accuracy. The engineering target is:

`deterministic calculation + verified educational explanation + safe fallback + professional review boundary`
